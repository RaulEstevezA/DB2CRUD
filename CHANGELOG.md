# Changelog

Notable changes to DB2CRUD, the web and the desktop version together. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/). Desktop releases will be tagged `v<version>` and published on [Releases](https://github.com/RaulEstevezA/DB2CRUD/releases).

## [Unreleased]

DB2CRUD starts from the code of Model2API (which continues as Controller2API), keeping what reads models and dropping what designs and writes an API: endpoints, OpenAPI, authentication, the framework generators and their project format.

### Added

- Web and desktop: reads Model2DB projects into the physical schema of the database (`db-schema`), with Model2DB's own code, for PostgreSQL, MySQL, MariaDB, SQLite, SQL Server and Oracle.
- Web and desktop: reads SQLAlchemy models into the physical schema, typed (`Mapped[...]` with `mapped_column`) or classic (`Column`): table arguments, association tables, indexes after the classes, Python enums (native, or text with a CHECK), defaults the database applies, computed columns and relationship names. Checked against the code Model2DB writes for every example and against the SQLAlchemy entities DB2CRUD writes, which read back as the schema they came from.
- Web and desktop: reads SQLModel models with the same reader: tables marked `table=True`, fields inherited from base models and mixins, `Field` options (`foreign_key`, `max_length`, `max_digits`, `sa_type`, `sa_column_kwargs`) or a whole `Column` in `sa_column`, and link tables. The SQLModel and SQLAlchemy code Model2DB writes for the same project read as the same schema.
- Web and desktop: reads Django models: tables named by `Meta.db_table` or by the app and the model, the implicit `id`, fields of abstract models, foreign keys and one-to-one fields with `to_field` and `db_column`, many-to-many tables (Django's own, or a `through` model), composite keys, `TextChoices` and `IntegerChoices`, `db_default`, `GeneratedField`, and `Meta` constraints (CHECKs written with `Q`), indexes and `unique_together`. The Django models DB2CRUD writes read back as the schema they came from.
- Web and desktop: reads Tortoise ORM models with the same engine as Django: tables named by `Meta.table` or by the model, the implicit `id`, integer keys numbered unless `generated=False`, `source_field`, foreign keys that cascade unless they say otherwise, many-to-many tables (`through` or Tortoise's own name, keyed by their two columns), and `CharEnumField`/`IntEnumField` as enums whose values are checked.
- Web and desktop: reads Prisma schemas: the engine from the datasource, `@map`/`@@map`/`@@schema`, native types (`@db.*`), defaults (also `dbgenerated`), `@updatedAt`, keys, uniques and indexes, relations with their actions (Prisma's defaults when they say none), implicit many-to-many tables (`_AToB`), scalar lists and enums (native, or text with a CHECK on SQLite). Prisma keeps no CHECK constraints: they are read from the SQL of `prisma/migrations` when it comes along, and a note says so when it does not. The `@@unique` of all the fields Prisma needs on a table with no key is not taken as a constraint. The Prisma schemas DB2CRUD writes read back as the schema they came from.
- Web and desktop: reads TypeORM entities: `@Entity` classes and the columns of the classes they extend, every column decorator (also the date, version and generated columns), types from the decorator or from the TypeScript type, enums (native, `simple-enum`, or a TypeScript enum kept as text), `@Unique`, `@Index` and `@Check`, foreign keys of `@ManyToOne` and `@OneToOne` (one or several `@JoinColumn`), `@JoinTable` tables, and the names TypeORM gives when none is written. The engine is the one the `DataSource` names, when it names only one. The TypeORM entities DB2CRUD writes read back as the schema they came from.
- Web and desktop: reads Sequelize models, declared with `Model.init` or `sequelize.define`: data types, `field`, keys, defaults (`literal`, `fn`, `NOW`, `UUIDV4`), `references`, enums (`ENUM`, or a TypeScript enum kept as text), arrays, table options (`tableName`, `indexes`, `schema`, `underscored`, `freezeTableName`, the defaults of `new Sequelize`), what Sequelize adds on its own (an `id`, the timestamps, `paranoid`), and the foreign keys and through tables of `belongsTo`, `hasOne`, `hasMany` and `belongsToMany`. The values `validate` allows (`isIn`, `min`, `max`, `len`) are read as CHECKs; a note says the database may have others Sequelize does not know. The Sequelize models DB2CRUD writes read back as the schema they came from.
- Web and desktop: reads Drizzle schemas for PostgreSQL, MySQL and SQLite: the columns as chains of calls (types, `notNull`, `primaryKey`, defaults with `sql`, `defaultNow`, `defaultRandom`, identity and computed columns, arrays, `references`), the constraints the third argument returns (`index`, `uniqueIndex`, `unique`, `primaryKey`, `foreignKey`, `check`), `pgSchema`, `pgEnum`, `mysqlEnum`, the `enum` option, `customType` and the navigation names of `relations`. The Drizzle schemas DB2CRUD writes read back as the schema they came from.
- Web and desktop: reads JPA entities, also with Hibernate's annotations (as Spring Data JPA uses them): `@Entity` classes with their `@MappedSuperclass` bases and `@Embeddable` parts, `@Table` (indexes, unique and check constraints), `@Column` and the type of each field (or its `columnDefinition`, or `@JdbcTypeCode`), keys (`@Id`, `@IdClass`, `@EmbeddedId`), generated values, `@ColumnDefault` and field initializers, `@Check`, `@OnDelete`, `@Comment`, foreign keys of `@ManyToOne` and `@OneToOne`, `@ManyToMany` join tables, and Java enums with the values the database keeps (by name, by a converter, or by position). The engine is the one the JDBC URLs name. The JPA entities DB2CRUD writes read back as the schema they came from (but for the key JPA makes a table without one carry).
- Web and desktop: reads EF Core models: the entity classes of the `DbSet<…>` of a context (or configured by `Entity<…>`) with their properties and data annotations, and the fluent API of `OnModelCreating` and of `IEntityTypeConfiguration<…>` (`ToTable`, `HasKey`/`HasNoKey`, `Property(…)` with its column, type, length, precision, defaults, computed and generated values, `HasIndex`, `HasAlternateKey`, check constraints, `HasOne`/`HasMany` relations with `HasForeignKey`, `OnDelete` and `UsingEntity`), C# enums with the values their conversion keeps, and EF Core's conventions where the code says nothing (table named by the `DbSet`, key `Id` numbered when it is an integer, foreign keys of navigations, cascade on a required relation). The engine is the provider the code uses. The EF Core models DB2CRUD writes read back as the schema they came from.
- Desktop: opens several files or a whole project folder as the database input (dropped or chosen), listed above the editor to see and edit each one; dependencies and builds (`node_modules`, `vendor`, `target`…) are left out. The web version reads one text and points to the desktop app for larger projects.
- Web and desktop: reads Eloquent from the Laravel migrations: each `Schema::create`, `Schema::table`, `Schema::drop` and `Schema::rename` with its Blueprint (column types and modifiers, `id()`, `timestamps()`, `softDeletes()`, `morphs()`, `foreignId()->constrained()`, `foreign()->references()->on()`, unique and index constraints, columns changed and dropped) and the SQL of `DB::statement`, in the order of the migrations and only what `up()` does; the models give each table its class, the enums they cast to, and the names of their relations. The engine is `DB_CONNECTION`, or the one the SQL shows. The Eloquent code Model2DB writes reads as the schema of its project.
- Web and desktop: reads SQL DDL for PostgreSQL, MySQL, MariaDB and SQLite, also the dumps of `pg_dump --schema-only` and `mysqldump --no-data`: `CREATE TABLE` (types, `NOT NULL`, defaults, identity and computed columns, comments, constraints of a column or of the table, MySQL keys), `CREATE INDEX`, `CREATE TYPE … AS ENUM`, `ALTER TABLE` (constraints and columns added, changed or dropped, defaults, sequences and identities) and `COMMENT ON`; functions, triggers, views and settings are left out, and an index on an expression gets a note. The engine is told from what only it writes. The DDL Model2DB writes for every engine reads as the schema of its project. The migrations of a Prisma schema are read with it.
- Web and desktop: reads Doctrine entities mapped with PHP attributes: `#[ORM\Entity]` classes with their mapped superclasses and embedded parts, `#[ORM\Table]`, `#[ORM\Index]`, `#[ORM\UniqueConstraint]`, `#[ORM\Column]` (or the PHP type of the property), keys and generated values, foreign keys of `#[ORM\ManyToOne]`/`#[ORM\OneToOne]` with their `#[ORM\JoinColumn]`, `#[ORM\ManyToMany]` join tables, PHP enums, and the DBAL types a project registers. Doctrine keeps no CHECK constraints but those of enums, and a note says so. The Doctrine entities DB2CRUD writes read back as the schema they came from, but for their foreign keys, which they keep as plain columns.
- Web and desktop: reads the application models (classes, DTOs, schemas in any language the importers read) in a tab of the database pane, and matches each with a table (one model in each direction: a `Request`, `Input` or `Command` is only written, a `Response` or `Output` only read) and each field with a column: by name, by the same words in another naming style, or by a lookup (`categoryName` for `category_id`, when the name is unique in that table); generated columns come from the database, lists from child or join tables. Each match carries its confidence and reason, and the conflicts between the model and the column (length, nullability, type, enum values) are shown on the table. Every match is a decision of the design: the model of each direction, the source of each column and the table of each list can be changed, with undo and redo, and those waiting for review are listed with the others.
- Web and desktop: reads Mapper projects (`mapper-project`) as application models: the model mapping named like a table relates it with the model on the other side, and each column follows the relation Mapper gives the field of its name. Relations that can be undone without loss (`direct`, `enum`, `epoch`, `arithmetic`) serve both directions; the others serve one and are left for review.
- Web and desktop: with application models in the language of the project (or in a format of no language), Projects in every language (Python, TypeScript, Java, C#, PHP, Kotlin, Rust and Swift) get a conversions module per table: the model into what the service takes (its create DTO, or the entity) and back, with lookups through the repositories, Mapper's transformations, values converted between the model's types and the columns' (in the typed languages: numbers of another size, text, dates and times, and enums by a switch; models read and built as the application has them, as records, with getters or public fields, setters, a builder, an object initializer or a constructor), and a `TODO` with the reason for what is left to the user (a field read from a hidden column the service never returns among them); and tests that read a stored row as the model and write it back. The model classes are copied into the project or imported from the user's module (a setting; in TypeScript, a declaration of that module keeps the project type-checking on its own; in the others, a copy in `application-models/` that the build or Composer loads while the folder exists). Models in another language get no conversions, and the project pane says why. Verified in Docker with SQLAlchemy, Django, TypeORM, Prisma, Drizzle, Sequelize, JPA, EF Core, Doctrine, Eloquent, Exposed, SeaORM and Fluent.
- Web and desktop: proposes the CRUD design of every table (its role, soft or hard deletes, version checks, rows that point to it, columns never returned; the queries of each repository and the operations of each service), each proposal with its confidence and its reason; what it is not sure about waits for the user. Every choice can be changed, with undo and redo.
- Web and desktop: writes Python + SQLAlchemy 2 projects with every setting as an option: entities (only the missing ones, all, none), repositories (interface, SQLAlchemy and in memory), services with entities or DTOs (Pydantic or dataclasses), transactions per operation, by the caller or per write, synchronous or asynchronous code, pages by offset or cursor, folders by layer or by table, get/find names, and tests; plus `crud-contract.json` for CRUD2Controller. ### Fixed

- SQLAlchemy on an existing database: columns named `metadata` or `registry` no longer break the entities, PostgreSQL arrays are mapped as `ARRAY` instead of JSON, types SQLAlchemy has no class for can be written on PostgreSQL, composite foreign keys keep `ON UPDATE`, and asynchronous MySQL and MariaDB projects stay on PyMySQL 1.1, since aiomysql cannot write binary values with 1.2.
- Every ORM is checked against databases created from their own SQL (`verification/ddl/`), and these no longer fail there:
  - PostgreSQL arrays, JSON and types an ORM does not know: Django, TypeORM, Prisma, Drizzle, Sequelize, JPA, EF Core, Doctrine, Eloquent, Exposed, SeaORM and Fluent write and read them in the type of the column. Prisma leaves alone the types its client cannot read (`interval`, `tsvector`…).
  - Schemas of PostgreSQL in Django, Drizzle (`pgSchema`) and Prisma (`@@schema`), and foreign keys across them in Sequelize.
  - Computed columns in Django (`GeneratedField`), which were written; field names Django refuses (`class_`, `save`).
  - Keys of bytes, unsigned integers, `TIMESTAMP`, `TIME` and MariaDB's `uuid` in Drizzle, SeaORM, Fluent, Doctrine and others.
  - Doctrine: names that are words of SQL, keys that hold a date (kept as text), times with a time zone.
  - Fluent: changing a row with an enum of PostgreSQL lost the changes of the columns before it; a key with a date found no row.
  - Swift without an ORM and Fluent kept bytes as JSON on MySQL and MariaDB.
  - TypeORM on MariaDB uses its `mariadb` driver, and no `char` on SQLite.
- Reading ORM code: Doctrine names between backticks, Drizzle foreign keys of a table to itself, Sequelize references with a schema, Django tables of another schema and computed columns written as `RawSQL`.
- Python: columns named like a type (`date`, `time`, `str`, `list`…) no longer break the entities and the DTOs.
