# Changelog

Notable changes to DB2CRUD, the web and the desktop version together. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/). Desktop releases will be tagged `v<version>` and published on [Releases](https://github.com/RaulEstevezA/DB2CRUD/releases).

## [Unreleased]

DB2CRUD starts from the code of Model2API (which continues as Controller2API), keeping what reads models and dropping what designs and writes an API: endpoints, OpenAPI, authentication, the framework generators and their project format.

### Added

- Web and desktop: reads Model2DB projects into the physical schema of the database (`db-schema`), with Model2DB's own code, for PostgreSQL, MySQL, MariaDB, SQLite, SQL Server and Oracle.
- Web and desktop: reads SQLAlchemy models into the physical schema, typed (`Mapped[...]` with `mapped_column`) or classic (`Column`): table arguments, association tables, indexes after the classes, Python enums (native, or text with a CHECK), defaults the database applies, computed columns and relationship names. Checked against the code Model2DB writes for every example and against the SQLAlchemy entities DB2CRUD writes, which read back as the schema they came from.
- Web and desktop: reads SQLModel models with the same reader: tables marked `table=True`, fields inherited from base models and mixins, `Field` options (`foreign_key`, `max_length`, `max_digits`, `sa_type`, `sa_column_kwargs`) or a whole `Column` in `sa_column`, and link tables. The SQLModel and SQLAlchemy code Model2DB writes for the same project read as the same schema.
- Web and desktop: reads Django models: tables named by `Meta.db_table` or by the app and the model, the implicit `id`, fields of abstract models, foreign keys and one-to-one fields with `to_field` and `db_column`, many-to-many tables (Django's own, or a `through` model), composite keys, `TextChoices` and `IntegerChoices`, `db_default`, `GeneratedField`, and `Meta` constraints (CHECKs written with `Q`), indexes and `unique_together`. The Django models DB2CRUD writes read back as the schema they came from.
- Web and desktop: reads Tortoise ORM models with the same engine as Django: tables named by `Meta.table` or by the model, the implicit `id`, integer keys numbered unless `generated=False`, `source_field`, foreign keys that cascade unless they say otherwise, many-to-many tables (`through` or Tortoise's own name, keyed by their two columns), and `CharEnumField`/`IntEnumField` as enums whose values are checked.
- Web and desktop: reads Prisma schemas: the engine from the datasource, `@map`/`@@map`/`@@schema`, native types (`@db.*`), defaults (also `dbgenerated`), `@updatedAt`, keys, uniques and indexes, relations with their actions (Prisma's defaults when they say none), implicit many-to-many tables (`_AToB`), scalar lists and enums (native, or text with a CHECK on SQLite). Prisma keeps no CHECK constraints: they are read from the SQL of `prisma/migrations` when it comes along, and a note says so when it does not. The `@@unique` of all the fields Prisma needs on a table with no key is not taken as a constraint. The Prisma schemas DB2CRUD writes read back as the schema they came from.
- Web and desktop: reads TypeORM entities: `@Entity` classes and the columns of the classes they extend, every column decorator (also the date, version and generated columns), types from the decorator or from the TypeScript type, enums (native, `simple-enum`, or a TypeScript enum kept as text), `@Unique`, `@Index` and `@Check`, foreign keys of `@ManyToOne` and `@OneToOne` (one or several `@JoinColumn`), `@JoinTable` tables, and the names TypeORM gives when none is written. The engine is the one the `DataSource` names, when it names only one. The TypeORM entities DB2CRUD writes read back as the schema they came from.
- Web and desktop: reads Sequelize models, declared with `Model.init` or `sequelize.define`: data types, `field`, keys, defaults (`literal`, `fn`, `NOW`, `UUIDV4`), `references`, enums (`ENUM`, or a TypeScript enum kept as text), arrays, table options (`tableName`, `indexes`, `schema`, `underscored`, `freezeTableName`, the defaults of `new Sequelize`), what Sequelize adds on its own (an `id`, the timestamps, `paranoid`), and the foreign keys and through tables of `belongsTo`, `hasOne`, `hasMany` and `belongsToMany`. The values `validate` allows (`isIn`, `min`, `max`, `len`) are read as CHECKs; a note says the database may have others Sequelize does not know. The Sequelize models DB2CRUD writes read back as the schema they came from.
- Web and desktop: reads Drizzle schemas for PostgreSQL, MySQL and SQLite: the columns as chains of calls (types, `notNull`, `primaryKey`, defaults with `sql`, `defaultNow`, `defaultRandom`, identity and computed columns, arrays, `references`), the constraints the third argument returns (`index`, `uniqueIndex`, `unique`, `primaryKey`, `foreignKey`, `check`), `pgSchema`, `pgEnum`, `mysqlEnum`, the `enum` option, `customType` and the navigation names of `relations`. The Drizzle schemas DB2CRUD writes read back as the schema they came from.
- Web and desktop: proposes the CRUD design of every table (its role, soft or hard deletes, version checks, rows that point to it, columns never returned; the queries of each repository and the operations of each service), each proposal with its confidence and its reason; what it is not sure about waits for the user. Every choice can be changed, with undo and redo.
- Web and desktop: writes Python + SQLAlchemy 2 projects with every setting as an option: entities (only the missing ones, all, none), repositories (interface, SQLAlchemy and in memory), services with entities or DTOs (Pydantic or dataclasses), transactions per operation, by the caller or per write, synchronous or asynchronous code, pages by offset or cursor, folders by layer or by table, get/find names, and tests; plus `crud-contract.json` for CRUD2Controller. Verified in Docker on PostgreSQL, MySQL, MariaDB and SQLite.
- Web and desktop: writes Python + Django 5.2 projects with the same settings (synchronous only: Django's transactions are), with models faithful to the database (composite keys, tables without a key left unmanaged, foreign keys with no index of Django's own) and pytest-django tests. Verified in Docker on PostgreSQL, MySQL, MariaDB and SQLite.
- Web and desktop: writes TypeScript + TypeORM 0.3 projects with the same settings (asynchronous, DTOs as interfaces or classes): an ES module with entities, repositories over an `EntityManager`, services, a unit of work whose transaction is the manager's, and Vitest tests. Verified in Docker on PostgreSQL, MySQL, MariaDB and SQLite.
- Web and desktop: writes TypeScript + Prisma 7 projects with the same settings: a Prisma schema that reflects the database (exact names, native types, keys, indexes, foreign keys with their actions, native enums), the client through the driver adapter of each database, plain entities the repositories convert Prisma's rows into (so services, DTOs and tests are those of every TypeScript project), and tests on a database Prisma creates from the schema. Verified in Docker on PostgreSQL, MySQL, MariaDB and SQLite.
- Web and desktop: writes TypeScript + Drizzle 0.45 projects with the same settings: the tables as the database has them (`src/schema.ts`, with keys, unique values, indexes, CHECK constraints, foreign keys and native enums), the database through the driver of each kind (node-postgres, mysql2, better-sqlite3), plain entities, and tests on a database created with the SQL drizzle-kit writes. Verified in Docker on PostgreSQL, MySQL, MariaDB and SQLite.
- Web and desktop: writes TypeScript + Sequelize 6 projects with the same settings: models that reflect the database (`src/models.ts`), the database through the driver of each kind (pg, mysql2, sqlite3), plain entities, transactions passed to every query, and tests on a database Sequelize creates from the models. Verified in Docker on PostgreSQL, MySQL, MariaDB and SQLite.
- Web and desktop: writes Java 21 + JPA (Hibernate 7) projects with no framework: entities faithful to the database (composite keys as `@IdClass` records, read-only relations so foreign keys exist, CHECK constraints, native enums), repositories over an `EntityManager` (interface, JPA and in memory), services with entities or DTOs (records or classes), JUnit tests, and a new setting for how updates come in typed languages: a `Patch<T>` per field, an `Optional<T>` per field or every field. Verified in Docker on PostgreSQL, MySQL, MariaDB and SQLite.
- Web and desktop: writes C# (.NET 10) + EF Core 9 projects with no web framework: plain entities mapped with the Fluent API as the database has them (keys, keyless tables, indexes, CHECK constraints, foreign keys with their actions, native enums of PostgreSQL through C# enums), async repositories over `AppDbContext` (interface, EF Core and in memory), services with entities or DTOs (records or classes), updates as a `Patch<T>` per field or every field, and xUnit v3 tests. Verified in Docker on PostgreSQL, MySQL, MariaDB and SQLite.
- Web and desktop: writes PHP 8.4 projects with Doctrine ORM 3 or Eloquent 12, with no framework: Doctrine entities mapped with attributes as the database has them, or Eloquent models with their casts and defaults (keys of several columns read and written by all of them); repositories (interface, database and in memory), services with entities or DTOs (readonly or plain classes), updates as a `Patch` per field, an array of the changed fields or every field, and PHPUnit 12 tests. Verified in Docker on PostgreSQL, MySQL, MariaDB and SQLite.
- Web and desktop: writes Kotlin (JVM) + Exposed 1.6 projects with no framework: plain entities and Exposed table objects as the database has them (keys, unique values, indexes, foreign keys with their actions, defaults, native enums through a column type of their own), repositories with Exposed's DSL (interface, database and in memory), services with entities or DTOs (data classes or plain classes), updates as a `Patch<T>` per field, an `Optional<T>` per field or every field, and kotlin.test tests on JUnit. Verified in Docker on PostgreSQL, MySQL, MariaDB and SQLite.
- Web and desktop: writes asynchronous Rust + SeaORM 2 projects with no framework: plain entity structs and a SeaORM description of each table as the database has it (keys, unique values, foreign keys with their actions, defaults, native enums kept as text), repositories behind async traits (database and in memory), services that return `Result<T, DomainError>`, a unit of work whose `begin()` and `commit()` group writes (a transaction dropped without a commit is rolled back), updates as a `Patch<T>` per field, an `Option<Option<T>>` per field or every field, and `cargo test` tests on Tokio. Verified in Docker on PostgreSQL, MySQL, MariaDB and SQLite.
- Web and desktop: writes Swift + FluentKit 1 projects (Fluent without Vapor) with async/await and strict concurrency: plain entity structs and a Fluent model of each table (`@CompositeID` for keys of several columns), repositories behind `Sendable` protocols (Fluent, and in memory on an actor), services that throw `DomainError`, updates as a `Patch<T>` per field, a double optional per field or every field, a `TimeOfDay` type for TIME columns, and swift-testing tests in one serialized suite. Verified in Docker on PostgreSQL, MySQL, MariaDB and SQLite.
- Web and desktop: reads application models in 23 formats with the importers of Mapper (code in 12 languages, JSON Schema, OpenAPI, GraphQL, Protocol Buffers, Smithy, Prisma, model schema, and JSON, YAML, XML or CSV documents), and the validations each field declares: Jakarta Bean Validation, class-validator, DataAnnotations, Symfony Validator, Laravel Data and Laravel rules, Pydantic, Django, JPA, SQLAlchemy, Prisma, Zod, Go tags and JSON Schema.
- Web and desktop: three built-in examples (Model2DB projects), and the page of the tool in English and Spanish, following the layout of the other tools.
- Its own icon: the database the tool reads, in grey, and the code it writes, in blue.
