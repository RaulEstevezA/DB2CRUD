# Decisions

Choices that shape the project, with the reason, so they are not undone by accident.

| Decision | Reason |
|---|---|
| No backend | Models and code may be private; everything DB2CRUD does fits in the browser (personal_web_style `UX_GUIDE.md`, local processing) |
| A desktop version in Python + PySide6, mirroring the web core | Same as the other tools of the suite; both versions pass the cases in `shared/test-cases/` |
| Importers start from Mapper's parsers and model | The suite should read a model the same way in every tool, and DB2CRUD reads application models in as many formats as Mapper, with the validations each field declares |
| Hand-written parsers instead of compilers or language servers | They run in the browser, need no downloads per language, never execute the user's code, and only have to find declarations |
| Deterministic rules, no AI | Every proposal must be repeatable and explainable; the user decides when the information is not enough |
| Pending decisions are never applied on their own | The generated code leaves a `TODO` where a pending decision goes (personal_web_style `patterns/confidence-states.md`) |
| Generated projects are written in English | Code, comments, README files and `TODO` markers of a backend project are read by any developer and usually in English; the interface language does not change the output |
| Generated projects are verified with Docker | Each language toolchain runs in its own container, so verification needs nothing installed on the machine but Docker, and the same runs work locally and in CI |
| A stack is recorded as verified only after `verification/` has built a generated project with it and its tests have passed | Producing files is not proof that they work |
| Cloudflare Web Analytics only counts visits | It is the site-wide beacon of personal_web_style `PUBLISHING.md`; it does not see the models or the generated code, and nothing about it is shown in the interface |
| Generated tests are part of every project and are what the verification runs | The same tests check the generator and later help the developer, instead of tests that only DB2CRUD sees |
| Inputs are never stored | Models and schemas may be private; only preferences (the language) are kept |
| Application models alone are accepted, without a database: repository interfaces to implement plus an in-memory implementation, no tables or ORM entities (2026-11-11) | It covers developers without a database yet without overlapping Model2DB, which designs databases; the inherited generators already write it |
| With DDL and no ORM, the user chooses how repositories reach the data: SQL with each language's official driver, or ORM entities reflected from the DDL (2026-11-11) | Reflecting entities from an existing database is exactly the "my database exists, I only want my models" case, and whoever does not want an ORM still has plain SQL |
| Without an ORM, each language uses its official or standard drivers: psycopg 3, MySQL Connector/Python and sqlite3 in Python; pg, mysql2 and better-sqlite3 in TypeScript; JDBC in Java and Kotlin; ADO.NET (Npgsql, MySqlConnector, Microsoft.Data.Sqlite) in C#; PDO in PHP; sqlx in Rust; SQLKit in Swift (2026-11-21) | They are what each language's documentation points to, with no layer above them, and one per database keeps the generated SQL readable. The tests create their tables from the schema's own DDL, written for each engine |
| A MongoDB collection is a table of `db-schema` whose columns are the fields of its documents; a nested document is a `json` column that says its `fields`, and an ObjectId a text marked as one (2026-11-24) | Every stage works on collections as on tables, and the relational generators keep seeing a JSON column and a text |
| Nested documents have no repository and no operations of their own: they are read and written with the document that holds them (2026-11-24) | They have no identity outside it |
| One item of a list can also be added or removed, in the database: by its `_id`, by its value when it is not a document, or by its position, which is refused when the list no longer has the size that was seen (2026-11-24) | Replacing the list whole undoes what another person added meanwhile |
| Document stacks store each write on its own unless the user chooses transactions (2026-11-24) | MongoDB has transactions on replica sets only, and a document is already written whole |
| Java reads and writes MongoDB with Spring Data as a library, over a `MongoTemplate` (2026-11-24) | It is what Java projects with MongoDB use; repositories stay classes of the project, with no Spring application to start |
| Python writes MongoDB with Beanie, behind plain dataclasses; nested documents are dictionaries typed with `TypedDict`, by their stored names (2026-11-24) | A Beanie document cannot be made without a database, and services and in-memory repositories must not need one; a dictionary keeps the fields the models do not know |
| A Beanie `Link` is read as the document Beanie stores (`{ $ref, $id }`), not as a foreign key (2026-11-24) | It is what the database has; read as an identifier, what the project wrote would not be what Beanie expects |
| Collections deduced from sample documents require a field only when 5 or more documents all have it, and deduce no unique values, limits or lists of values (2026-11-24) | A rule deduced by mistake refuses good documents; one that is missing only checks less. Lists of values would also copy data of people into the code |
| A field of sample documents is a foreign key when its identifiers are those of another collection, never by its name (2026-11-24) | An ObjectId is not repeated between collections, so the match is proof; a name is a guess |
| A Model2DB project for MongoDB takes its fields from the validators Model2DB builds, whatever its output, and from the output only what that library stores differently: UUIDs, DBRefs of Beanie, identifiers of Spring (2026-11-25) | The validators say more than the classes (sizes of numbers, what is required), but documents must be read as they are stored |
| A `ref` to a collection the input declares is a foreign key the services check; nothing is guessed from names (2026-11-24) | MongoDB checks no references, so the service is the only one that can; a collection pasted alone works without them |
| A change of a document writes only the fields that differ from what was read, and keeps the ones the models do not know (2026-11-24) | Documents hold more than one program knows, and two people changing different fields must not undo each other |
| The physical schema has a common format, `db-schema`, that Model2DB will export; until it does, DB2CRUD recalculates it with copies of Model2DB's parsers, `design/` and `physical/` (2026-11-11) | `model2db-project` stores the input text and design decisions, not the schema. A shared format avoids duplicating Model2DB's logic for good, and it is also DB2CRUD's internal model: the DDL and ORM-code importers produce the same thing |
| DB2CRUD generates the services, not only the repositories (2026-11-11) | Validation from the constraints, unique checks, database lookups (`categoryName` → `categoryId`), model ↔ entity conversions and domain errors all depend on the schema, and DB2CRUD is the only tool in the chain that knows it; CRUD2Controller then writes thin controllers over finished services |
| The first stack taken end to end is Python + SQLAlchemy 2 + PostgreSQL (2026-11-11) | Model2DB already generates SQLAlchemy, and the inherited code has it verified in Docker, so the new path is checked against known, working output before other stacks follow |
| Every choice that is a matter of taste or of the surrounding project is a setting with all its options generated; the recommended one is only the default (2026-11-11) | The user knows the project the code goes into; DB2CRUD foresees the options instead of choosing for them (docs/design.md, section 4) |
| Defaults: services take and return the application models, or the entities when there are none; models in another language are written again in the stack's; one transaction per service operation; synchronous code (2026-11-11) | Answers of the design review: no invented DTOs, models usable by the services, operations that happen whole, the simplest code to read. Each is a setting |
| Python + SQLAlchemy is generated synchronous and asynchronous (2026-11-11) | Both styles are common in Python projects; each is verified on its own |
| Services of typed languages (Java first, then C#, Kotlin, Swift, Rust) take partial updates in the way a setting chooses: `Patch<T>` per field (absent, null or a value; the default), `Optional<T>` (null when not sent) or the whole set of changeable fields (2026-11-12) | Those languages have no partial object like TypeScript's or Python's; each way is common, and the project around the code decides which one fits |
| C# uses EF Core 9 on .NET 10, and offers updates as a `Patch<T>` or every field (2026-11-12) | Pomelo, the provider of MySQL and MariaDB, is on EF Core 9, and EF Core 11 needs .NET 11; .NET has no `Optional<T>`, and writing one would repeat `Patch<T>` |
| Java writes plain JPA over an `EntityManager` (Hibernate), not Spring Data (2026-11-12) | The data access layer stays free of any framework; CRUD2Controller adds the framework. Spring Data repositories can become another option later |
| PHP 8.4 offers Doctrine ORM 3 and Eloquent 12 standalone (`illuminate/database` through Capsule), with no framework; updates come as a `Patch` per field (the default), an array of the changed fields or every field; DTOs are readonly or plain classes (2026-11-18) | Both ORMs are common outside Laravel and Symfony, and CRUD2Controller adds the framework. PHP has no `Optional<T>`, and an array of the given fields is its own partial object |
| Eloquent repositories read and write a row by every column of its key with the query builder (2026-11-18) | Eloquent keys a model by one column: `save()` cannot update or delete a row whose key has several columns, or none |
| Doctrine maps a table without a primary key by the columns that can be compared as text (2026-11-18) | Doctrine needs an identifier and keys its rows by it as text: a date in it breaks the identity map. The tests create the table without a key, as it is |
| Kotlin writes Exposed's DSL (table objects and queries over JDBC), not its DAO, with plain entity classes whose properties are all nullable (2026-11-19) | The DAO ties entities to a transaction and keys a row by one column; the DSL reads and writes any table, keys of several columns or none included. Properties start empty so an entity can be built field by field, as the other languages do |
| In Kotlin, `optional` updates use `java.util.Optional` (2026-11-19) | Kotlin has no Optional of its own; a nullable `Optional<T>?` tells "not sent" (null) from "set to null" (`Optional.empty()`), as in Java |
| Native enums are Exposed columns of a type of their own (`DatabaseEnum`), kept as their text (2026-11-19) | Exposed's enum columns need a Kotlin enum per database enum; the text keeps the entities as plain as in the other languages, and PostgreSQL gets its value as a `PGobject` of the enum |
| On MariaDB, Kotlin keeps a timestamp with a time zone as an `Instant` (2026-11-19) | Exposed has no timestamp with a time zone on MariaDB; an `Instant` is the point in time the value stands for, which is what such a column holds |
| Rust writes SeaORM 2, asynchronous only, and its services return `Result<T, DomainError>`; DTOs are plain structs (2026-11-19) | SeaORM has no synchronous API, and Rust has no exceptions: a `Result` is how its code says an operation failed. Derives such as serde's belong to whoever puts the DTOs on the wire (CRUD2Controller) |
| The Rust unit of work opens a transaction with `begin()` and keeps it with `commit()`; one dropped without a commit is rolled back (2026-11-19) | SeaORM's closure-based transactions cannot borrow the service's state; a unit of work per transaction, behind a trait object, is how Rust code usually does it, and an early return with `?` rolls back on its own |
| Without repository traits, Rust projects have no in-memory repositories, and their service tests run on the database (2026-11-19) | Rust has no inheritance: without a trait nothing can stand in for the database repository, so the setting cannot be honoured |
| SeaORM keys a table without a primary key by its columns that cannot be null and can be indexed; the repositories still tell its rows apart by all of them (2026-11-19) | SeaORM needs a key, and MySQL cannot index a TEXT or BLOB column without a length |
| In Rust, native enums stay text: SeaORM casts them in PostgreSQL (`select_as`, `save_as`) (2026-11-19) | The entities stay as plain as in the other languages, with no Rust enum per database enum |
| Swift writes FluentKit without Vapor, async/await with strict concurrency, and its services throw `DomainError` (2026-11-19) | Fluent's models and drivers work without the framework, and CRUD2Controller adds Vapor. Throwing is Swift's way of failing |
| Without repository protocols, the Swift in-memory repository is a subclass of the database one (2026-11-19) | Swift has inheritance, as Kotlin does, so the setting can be honoured; the rows are kept in an actor |
| Swift repositories insert only the values given, through the query builder, instead of `Model.create` (2026-11-19) | `create` sends DEFAULT for every field not set, and SQLite takes it as NULL, so the database never fills its defaults |
| Swift keeps a TIME column as a `TimeOfDay` of its own (2026-11-19) | Swift has no time of the day, and the drivers do not read a TIME into a Date; on PostgreSQL it says how the database keeps one |
| ORM code is read into the same `db-schema` as a Model2DB project, one reader per ORM over a small expression tree that never runs the code; the engine stays unknown (`dialect: null`) and the settings choose it (2026-11-19) | ORM code is valid for several engines and rarely says which; reading the declarations, not running them, keeps the input in the browser and works with code that does not compile |
| An ORM reader is checked against the code Model2DB writes for each example (`shared/test-cases/orm/model2db/`, written by `scripts/orm-fixtures.mts`): it must find what the project says, and may find more (a length) (2026-11-19) | The same project read two ways must give the same database; hand-written cases (`orm/hand/`) cover the forms Model2DB never writes |
| SQLModel is read by the SQLAlchemy reader with a flavour of its own (which classes are tables, how `Field` becomes a column, how relationships are named) (2026-11-19) | SQLModel is SQLAlchemy underneath: the types, keys, table arguments and enums are the same, so only the declarations differ |
| Django's `on_delete` is read as the action of the foreign key (`PROTECT` and `DO_NOTHING` as none), as Model2DB writes it (2026-11-19) | Django emulates it in the application, but it is what the code means the database to do, and what the CRUD design needs |
| A Django foreign key has the index Django gives it, unless the primary key or another index already starts with its column; a model with `managed = False` has only the indexes of its `Meta`, and a note says its key may be the ORM's only (2026-11-19) | That is the database Django creates; a covered index adds nothing, and Django creates nothing for an unmanaged model |
| Django and Tortoise are read by one engine for ORMs of field classes (`fieldModels.ts`) with a flavour each (2026-11-19) | Both declare a table as a class of field objects with a `Meta`; only names, defaults and many-to-many tables differ |
| Tortoise's enum fields are read as an enum with a CHECK, though Tortoise checks the values in the application (2026-11-19) | The rules need the values to validate them in the services, as a CHECK makes them do |
| Prisma's CHECK constraints are read from the SQL of its migrations when it comes with the schema; without it, a note says Prisma keeps none (2026-11-19) | Prisma has no CHECK, and the comment DB2CRUD writes about them is free text; the migrations are what the database got |
| A Prisma model with no key and a `@@unique` of all its fields has no unique constraint, and a note says so (2026-11-19) | Prisma needs a unique set of fields on every model; as Django's `managed = False`, it lives only in the ORM |
| TypeORM's engine is read from the `DataSource` only when it names one engine; otherwise the settings choose it (2026-11-20) | DB2CRUD's own data source chooses the engine from the URL at run time, so the code alone does not say it |
| A TypeORM property typed with a TypeScript enum over a text column is read as an enum checked by a CHECK (2026-11-20) | That is how Model2DB writes enums for TypeORM; the values are what the rules need |
| Sequelize's `validate` (`isIn`, `min`, `max`, `len`) is read as CHECKs, and the actions of its foreign keys only as the code declares them (2026-11-20) | Sequelize keeps no CHECK, but those values are what the rules need; the actions it would choose apply only when it creates the tables, which DB2CRUD never assumes |
| JPA's `cascade = ALL`/`REMOVE` or `orphanRemoval` on the side a foreign key points to is read as ON DELETE CASCADE, and a field initializer as the column's default (2026-11-20) | That is what the code means the database to do with those rows and values, as Model2DB writes it; `@OnDelete` and `@ColumnDefault` win when given |
| A JPA entity keeps the key it declares, even one of all its columns (2026-11-20) | JPA needs a key on every entity, and nothing in the code tells one made for a table without a key from a real composite key |
| EF Core's conventions apply where the code says nothing: a relation it does not configure has the key and the delete behaviour EF Core gives it (cascade when it is required) (2026-11-20) | They are what the migrations of that model create, and DB2CRUD's own EF Core code states every relation |
| SQL DDL is read by one reader for every engine, which tells the engine from what only it writes; an INTEGER PRIMARY KEY declared on its column is numbered in SQLite, one declared on the table is not (2026-11-20) | The engines share most of the syntax; that is how Model2DB writes an identity in SQLite, and the rowid is only kept when asked for |
| The web version reads one text; the desktop version also opens several files or a whole project folder, and the web points to it for larger work (2026-11-20) | The web stays light and step by step; reading a whole project is heavier work and easier in Python on the user's computer. The core is the same: the readers take a list of files |
| Eloquent is read from the Laravel migrations, each Blueprint written as the DDL it stands for and read by the DDL reader; the models only name tables, enums and relations (2026-11-20) | Eloquent's models declare no columns: the migrations are what made the database |
| The migrations of a Prisma schema are read with the DDL reader, in the order of their names (2026-11-20) | They are SQL, applied in that order; one reader keeps CHECK constraints, drops and renames consistent |
| An application model matches a table by its name without the suffixes `Entity`, `Model`, `Dto`, `Record`, `Request`, `Input`, `Command`, `Response` and `Output`, in the singular; a field matches a column by its name or by the same words in another naming style, both exact (reviewed by Raúl, 2026-11-20) | The same rules name things in every language; `createdAt` for `created_at` is the usual difference between code and SQL |
| A `Request`, `Input` or `Command` only goes into its table and a `Response` or `Output` only comes out of it: a table takes one model of each direction, each matched on its own; several of one direction wait for review (2026-11-20) | A request and a response for the same table are the usual pair, not a doubt; a model that only reads is checked the other way (a column that may be null, values the model does not know) |
| A field the model may leave out but that has a value of its own is not a conflict for a required column, and the values of an enum are compared only when its type fits the column (2026-11-20) | It always sends a value; a type that does not fit already says why the values differ |
| A field `<x><Column>` for a foreign key `<x>_id` is a lookup by that column of the target table: probable when it is unique, for review otherwise (2026-11-20) | A unique name finds one row; a name that is not unique could find several, so the user decides |
| A column with no field is filled by the database when it is generated, and is a conflict when it is NOT NULL without a default (2026-11-20) | An insert would fail on such a column, so it is said before any code is written |
| When the services convert the models (reviewed by Raúl, 2026-11-20): a lookup that finds no row throws a clear error and never creates one; a required column with no field gets a `TODO`; list fields are always read and saved only when a setting says so; a conflict never stops the generation, and becomes a validation in the service where it can, a `TODO` where it cannot | Nothing ambiguous is applied on its own, and choices of taste are settings |
| A Mapper project is read as application models: the model mapping named like a table relates it with the model on the other side, for both directions; a relation serves the other direction only when its transformation can be undone without loss (`direct`, `epoch`, `arithmetic` by a number other than 0, `enum` one to one without fallback), and is left for review otherwise (2026-11-20) | Mapper's relations go one way and a service needs both; inverting only what is lossless keeps the generated code right, and the rest becomes a `TODO` instead of a guess |
| Conversions between the application models and the tables are generated only when the models are written in the language of the project; otherwise the services keep their DTOs and a message says why there are no conversions (decided by Raúl, 2026-11-20) | A conversion is code in the project's language over the user's classes: models in another language cannot be used as they are |
| The services keep taking and returning their DTOs; a conversions module per table turns the application model into the DTO (lookups, Mapper transformations, `TODO`s) and back (decided by Raúl, 2026-11-20) | The services and the `crud-contract` stay the same whether there are models or not, so CRUD2Controller does not change |
| A setting chooses where the application model classes come from: a copy written into the project from what was read (default: the project builds and is verified on its own), or an import from the user's module, with a copy for the tests only (decided by Raúl, 2026-11-20) | A choice of taste: every option is generated |
| The application models are read in a tab of the database pane, and their matching is part of the CRUD design: proposed again when the models or the database change, keeping the user's choices, and undone with the other decisions (2026-11-20) | One history and one review list for every decision; the generators will read the matching from the design |
| DB2CRUD's Django models say `db_index=False` on every foreign key (2026-11-19) | The indexes of the database are written in `Meta`: Django's own would be one the database does not have |
